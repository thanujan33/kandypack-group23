## Executive Summary

KandyPack is a **rail-and-road distribution management system** for a Sri Lanka logistics business. The project has matured significantly and represents a **genuinely sophisticated database-centric architecture** for an undergraduate project — well above what is typically expected at this level. That said, there are notable rough edges in the frontend, some backend gaps, and a few correctness issues worth fixing before a final submission or demo.

**Overall Rating: 8.5 / 10** for architecture sophistication.

## 2. Architecture Strengths — What's Impressive

### 2.1 Database Layer is the Star

This is not a typical "put everything in Node.js" student project. The team has pushed substantial business logic into MySQL, which is the correct approach for a DB-systems course.

**Stored Procedures with full transactional integrity:**
- `sp_place_order` — validates customer, route, items, lead time, duplicate products, and integer quantities *inside the DB*
- `sp_allocate_order` — greedy bin-packing allocation across multiple trains using a **cursor loop**, handling partial capacity splits. This is genuinely complex procedural SQL.
- `sp_dispatch_train`, `sp_receive_allocation` — proper state-machine transitions
- `sp_schedule_delivery`, `sp_dispatch_delivery`, `sp_cancel_delivery`, `sp_return_delivery` — full road trip lifecycle, each transactional and idempotent

**All critical procedures use `SELECT … FOR UPDATE` on `app_lock`** — a deliberately simple but effective pessimistic locking strategy that prevents race conditions (the concurrency test validates this explicitly).

**Triggers doing real work:**
- `orders_lead_insert/update` — 7-day lead time enforcement at the DB level
- `allocation_guard` — capacity check + order-to-store alignment on every INSERT
- `allocation_immutable` — received quantities cannot decrease; identity fields cannot change
- `train_edit_guard` — locks timetable once allocations exist
- `road_insert_guard` / `road_update_guard` — calls `sp_check_roster` which enforces:
  - No resource (truck/driver/assistant) overlaps
  - Driver 30-minute rest between routes
  - Assistant max 2 consecutive routes before a break
  - Weekly hour limits (driver 40h, assistant 60h) **including planned-but-not-yet-dispatched hours**

**SQL Functions:**
- `fn_work_minutes` — calculates committed minutes for an employee in a rolling ISO week window, correctly splitting trips that cross Sunday midnight (tested explicitly)

**Views used as building blocks:**
- `v_order_totals` — computed totals via generated columns
- `v_train_capacity` — real-time available capacity
- `v_trip_windows` — normalises actual vs planned time windows
- `v_sales_lines`, `v_staff_windows` — flattened projections used by complex report queries

**Audit log with append-only enforcement** — generated by a JS migration that programmatically creates triggers for 7 tables × 3 actions = 21 triggers. Attempts to UPDATE or DELETE from `audit_log` are blocked by a trigger at the DB level. This is a production-quality pattern.

**Generated columns** (`line_total`, `space_used`) eliminate redundant calculation and keep totals in sync automatically.

**ENUM columns** for state machines — correct use of MySQL's native type system.

### 2.2 Backend Node.js Layer

**Auto-discovery of route modules** via `readdir` + dynamic `import()` sorted alphabetically — clean plugin-style architecture. Adding a new module requires only dropping a `.routes.js` file.

**`db.js` connection wrapper** centralises:
- Timezone pinning (`+05:30`) on every acquired connection
- `READ COMMITTED` isolation level (appropriate for this workload)
- `@actor` session variable (used by audit triggers)
- Automatic cleanup before returning connections to pool

**`http.js` utility functions** (`fail`, `int`, `text`, `roles`, `checkStore`) form a tiny validation micro-library — consistent, reusable, no external library bloat.

**Error handler maps MySQL error codes to HTTP status codes** — `45000` → 409, `ER_DUP_ENTRY` → 400. Clients receive meaningful messages without stack traces.

**Auth is correctly implemented:**
- bcrypt with cost 12
- JWT HS256 + server-side session table (hybrid — token can be revoked)
- 30-minute idle session expiry enforced server-side on every request
- In-memory rate limiter (acknowledged as demo-only in a code comment)
- JWT secret validated for length and not-default value at startup

### 2.3 Testing Infrastructure

The test setup is **unusually strong** for a student project:

- Tests run against a **real MySQL instance** in a uniquely-named scratch database, dropped after the run
- `test.js` orchestrates: create DB → migrate → seed → run tests → drop DB
- CI pipeline (GitHub Actions) runs this on every push/PR against MySQL 8.4
- `integration.test.js` tests DB constraints directly (lead time, concurrency, hour limits, ISO-week boundary, audit immutability)
- `api.test.js` tests role-based access, report endpoints, state transitions via HTTP
- The concurrency test (`Promise.allSettled` with two simultaneous allocations) is a genuine race condition test

### 2.4 DevOps

- Docker + `compose.yaml` with health-checked MySQL dependency
- `profiles: [full]` pattern to run DB-only during development
- Dockerfile correctly layers dependency installation before code copy
- `engines: {node: ">=24 <25"}` pins the runtime version

## 3. Errors & Bugs Found

### 🔴 Critical

**`road.routes.js` — SQL injection risk in `PATCH /road/:kind/:id/active`**

```js
// road.routes.js L122-124
const [row] = await read(`SELECT store_id FROM ${table} WHERE id=?`, [id]);
await transaction(req.user.id, c => c.execute(`UPDATE ${table} SET active=? WHERE id=?`, ...));
```

`table` is derived from a whitelist (`{ trucks:'trucks', employees:'employees' }`) so it is *currently* safe — but this pattern is fragile. The only guard is `if(!table) fail(...)` at L116.

> **Fix**: Use a strict allowlist assertion instead of a truthiness check, e.g. `const ALLOWED = new Set(['trucks','employees']); if(!ALLOWED.has(table)) fail(...)`.

---

**`auth.js` — `authenticate` middleware silently swallows all errors**

```js
// auth.js L68
} catch { next(Object.assign(new Error('Session expired; sign in again'), {status:401})); }
```

Any exception — DB crash, network timeout, programming error — is silently converted to a 401. A DB outage would look like "session expired", making debugging impossible.

> **Fix**: Inspect the caught error. Only convert `JsonWebTokenError`/`TokenExpiredError` to 401. Re-throw or forward others with their original status.

---

### 🟡 Medium

**`orders.routes.js` — No format validation on date filter params**

```js
if(req.query.from){where+=' AND o.placed_at>=?'; params.push(req.query.from);}
if(req.query.to){where+=' AND o.placed_at<DATE_ADD(?,INTERVAL 1 DAY)'; params.push(req.query.to);}
```

Values are parameterised (not injectable), but no format check. An invalid date string is silently coerced by MySQL. Compare with `reports.routes.js` which already validates with a regex.

> **Fix**: Add `/^\d{4}-\d{2}-\d{2}$/.test(req.query.from)` before pushing.

---

**`road.routes.js` — Unhelpful error when ADMIN omits `store_id` from `/road/resources`**

```js
const store = req.user.role === 'STORE' ? req.user.store_id : int(req.query.store_id);
```

If an ADMIN forgets `?store_id=`, the error "ID must be a positive integer" doesn't name the parameter.

> **Fix**: `int(req.query.store_id, 'store_id')` or an explicit `fail('store_id query param is required', 400)`.

---

**`rail.routes.js` — `PUT /trains/:id` returns 200 even when no rows were updated**

```js
await transaction(req.user.id, c => c.execute(`UPDATE train_trips SET ... WHERE id=? AND status='SCHEDULED'`));
res.json({message: 'Unallocated train updated'}); // Always 200
```

If the train ID doesn't exist or the train is already allocated, 0 rows are updated and the client still gets a success response.

> **Fix**: Destructure `affectedRows` from the result and `fail('Train not found or already allocated', 404)` if it's 0.

---

### 🟢 Minor / Style

**`frontend/src/main.jsx` — Inline Tailwind classes mixed with `style.css`** — inconsistent styling approach; the header uses arbitrary Tailwind values (`bg-[#12203A]`) but a vanilla CSS file also exists.

**`frontend/src/modules/road/Page.jsx` — 471 lines, monolithic** — manages 10+ state variables in one component. Sub-components for Trucks, Employees, DeliveryPlanner, and ReturnLog would improve maintainability.

**`extract.js` at the project root is untracked** — 538-byte scratch file not in `.gitignore` and not committed. Should be cleaned up.

## 4. Possible Improvements

### Architecture

| # | Improvement | Impact |
|---|---|---|
| 1 | **Pagination on list endpoints** (`/orders`, `/rail/manifest`) | High — will break with large datasets |
| 2 | **`sp_refresh_order` called in a cursor loop** in `sp_dispatch_train` — batch UPDATE via subquery would be faster | Medium — performance at scale |
| 3 | **Shared rate limiting** (currently in-memory Map) won't work with multiple Node instances | Medium |
| 4 | **No HTTPS/TLS termination** in Dockerfile — assumes a reverse proxy; should be documented | Low |
| 5 | **`multipleStatements: false`** is correct but never explicitly tested | Low |

### Database

| # | Issue | Fix |
|---|---|---|
| 6 | `routes.coverage_area` has a `UNIQUE` constraint — awkward for overlapping zones | Relax to a non-unique index |
| 7 | `sessions` table accumulates stale rows with no cleanup | Add a scheduled `DELETE FROM sessions WHERE expires_at < NOW() - INTERVAL 30 DAY` |
| 8 | `audit_log` has no partitioning or archival strategy — grows unbounded | Partition by month or add a retention policy |

### Frontend

| # | Improvement | Impact |
|---|---|---|
| 9 | **No global loading indicators** — the page freezes silently during API calls | UX |
| 10 | **No `<ErrorBoundary>`** — any JS runtime error crashes the entire app tab | Robustness |
| 11 | **`week` defaults to `''`** in Road page — sent to backend as empty string, causing silent MySQL NULL coercion | Correctness |
| 12 | **`sessionStorage` for JWT** — token lost on tab close; consider `localStorage` with explicit logout, or document the tradeoff | UX |
| 13 | **`Table` uses row index as `key`** — causes React reconciliation issues if rows are reordered | Minor correctness |
| 14 | **No customer-facing order placement UI** — backend fully supports it, no frontend module | Missing feature |

## 6. Correctness of the `npm run dev` Error

The error you saw (`npm error Missing script: "dev"`) was because you ran `npm run dev` in the **root workspace**, which intentionally has no `dev` script. The correct commands are:

```powershell
# Run in the project root in two separate terminals:
npm run api    # starts backend (Node --watch on port 3000)
npm run web    # starts frontend (Vite on port 5173)
```

The frontend is currently running via `npm run web`. The backend needs `npm run api` in a separate terminal.
